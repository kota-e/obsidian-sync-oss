### 0.4 実装する方式の要約

ローカルには普通のMarkdownファイルを置く。R2には次の三つを置く。

1. **本文の保管庫（blob）**：内容の異なる版を、別々のキーに保存する。
2. **一覧表（manifest）**：どのパスが、どの本文を指しているかを記録する。
3. **最新一覧へのポインタ（head）**：現在採用する一覧を指す小さな記録。

本文と一覧を先に保存・確認し、最後にheadだけを条件付きで切り替える。
他端末が先にheadを更新していたら、上書きせず計画を作り直す。

これは本書で提案する独自プロトコルであり、Remotely Saveの現行プロトコルの説明ではない。
**既存Remotely Saveのリモート領域に、そのまま接続して置き換えられる互換性は約束しない。** 初期移行は、確認済みのローカルコピーから新しい領域に取り込む。

採用理由は、複数オブジェクトの同時更新をストレージ側が自動で一体化すると仮定せず、公開する同期状態を一本化できるためである。代償として、一覧の保存容量、実装量、既存コードからの変更量が増える。ベース監査で改修量を評価し、別方式へ変更する場合は設計記録とテスト条件を更新する。

### 0.5 根拠と設計案の区別

R2の条件付きPUT、整合性、API範囲はCloudflareの一次資料を確認した。[S1][S2]

以下の状態表・プロトコル・しきい値・試験基準は、その制約の下で作成した**本プロジェクトの設計案**である。

# 1. 同期状態の判定方法

## 1.1 同期の単位と対象

**SYN-001** ファイルを基本単位とする。フォルダはファイルの相対パスから必要に応じて作成する。空フォルダ自体の同期は行わない。

MVP 0.1の対象は拡張子`.md`の通常ファイルとする。拡張子の判定は大文字小文字を区別しないが、実際のファイル名を勝手に変更しない。

`.obsidian`、実際の`app.vault.configDir`、`.trash`、`.git`、本プラグインの内部領域、シンボリックリンク等の特殊ファイルは対象外とする。その他のドット始まりのパスも初期版は対象外とし、対象外一覧を表示する。アンダースコア始まりは一律除外しない。

対象外を「削除済み」と解釈してはならない。添付ファイルを同期していない場合、Markdown中の画像リンク等が他端末で表示できない可能性を初期画面で伝える。

## 1.2 比較する三つの状態

| 記号 | 意味 | 保存・取得元 |
|---|---|---|
| `L` | この端末で実際に読めた現在のファイル | ローカルVault |
| `R` | 検証済みのリモートmanifestが示す版 | R2 |
| `B` | この端末とR2の間で最後に一致・反映を確認した版 | 端末固有のbaseline |

`B`は「最後に同期ボタンを押した時刻」ではない。**ファイルごとの共通版の証拠**である。
競合・失敗・保留のファイルでは`B`を進めない。

**SYN-002** 更新判定の本体はSHA-256による内容比較とする。更新日時やファイルサイズだけで変更有無・優先順位を決めない。
`mtime`は表示・診断用の補助情報とし、端末時計の進み遅れがあることを前提とする。
R2のETagは条件付き更新のための不透明な値として扱い、本文のSHA-256の代用にしない。

## 1.3 内容の取り扱い

- 本文ハッシュは保存する元のバイト列全体を対象とする。空ファイルも有効な内容である。
- MarkdownはUTF-8として厳密に検査する。読み込みと再エンコードで同じバイト列を再現できない場合、`E_UNSUPPORTED_ENCODING`として停止する。
- BOM、CRLF/LF、末尾改行、空白を自動整形しない。文字コードや改行コードの変更機能は実装しない。
- 内容のUnicode正規化は行わない。パスの正規化と本文の扱いを混同しない。
- SHA-256の衝突耐性は内容識別の前提であり、データを変更できる第三者に対する署名・改ざん認証ではない。
- ローカル読み取り中に変更イベントが発生した場合、取得をやり直す。書き込み直前にも内容を再確認する。

初期版では全対象ファイルをハッシュ検査する。`mtime`キャッシュによる読み取り省略は最適化として後回しにする。

## 1.4 ローカル状態の分類

| 状態 | 条件 | 判断 |
|---|---|---|
| `LIVE` | 読み取り成功、パス・サイズ・エンコードが有効 | ハッシュ比較できる |
| `ABSENT` | 完全なローカル走査と個別確認で不在 | 不在であって削除承認ではない |
| `UNREADABLE` | 権限、I/O、プレースホルダー、途中エラー | 不在扱いせず停止 |
| `EXCLUDED` | 同期対象外ルールに合致 | 同期も削除も実行しない |
| `UNSTABLE` | 読み取りと実行確認の間に変更 | その計画を無効化する |
| `PATH_CONFLICT` | 大文字小文字等で同じ保存先に衝突 | 書き込み禁止 |

一度不在になって次の同期で復活したファイルも、内容とbaselineを比較する。不在の間に削除したという推測はしない。

## 1.5 リモート状態の分類

| 状態 | 条件 | 判断 |
|---|---|---|
| `LIVE` | manifestに有効な本文参照がある | 検証後に比較・取得できる |
| `TOMBSTONE` | 明示的な削除記録がある | 第5章の削除規則を適用 |
| `ABSENT_NEW` | 共通版のないパスがmanifestに存在しない | 未登録の可能性がある |
| `MISSING_UNEXPECTED` | baselineにあったパスが削除記録なしで消えた | メタデータ異常として停止 |
| `UNREADABLE` | head、commit、manifest、必要な本文が取得できない | 不在扱いせず停止 |
| `UNSUPPORTED` | 未対応の形式・必須機能が指定された | 書き込み禁止 |

S3のオブジェクト一覧からノートの削除を推測しない。通常同期の正式な一覧は、headが指す不変manifestとする。

## 1.6 baselineがある通常同期の判定表

以下では`b`を前回共通版のハッシュ、`x`と`y`を`b`と異なる内容とする。まず双方が読めることが前提。

| ID | L | R | 判定 | MVP 0.1の動作 |
|---|---|---|---|---|
| ST-01 | b | b | 変更なし | 書き込みなし |
| ST-02 | x | b | Localだけ変更 | 旧版参照を保持したままUpload計画 |
| ST-03 | b | x | Remoteだけ変更 | ローカル旧版を保全してDownload計画 |
| ST-04 | x | x | 双方が同じ結果 | 内容検証後baselineを更新。本文の書き換え不要 |
| ST-05 | x | y、x≠y | 双方が別々に変更 | 競合。同期全体を実行前に停止 |
| ST-06 | 不在 | b | Localで不在 | 削除候補を表示。削除も自動復活も行わない |
| ST-07 | 不在 | x | Local不在・Remote変更 | 削除対編集の競合。停止 |
| ST-08 | bまたはx | 削除記録なしの不在 | Remote異常 | `E_REMOTE_ENTRY_LOST`で停止 |
| ST-09 | 不在 | 削除記録なしの不在 | 双方不在でも証拠不足 | `E_REMOTE_ENTRY_LOST`で停止 |
| ST-10 | 任意 | TOMBSTONE | 削除記録を発見 | 初期版は未対応機能として停止。0.3の規則へ |
| ST-11 | 読めない/不安定 | 任意 | 状態不確実 | 書き込み開始前に停止 |

ST-06で自動復活させないのは、「消したノートが勝手に戻る」動作を避けるためである。ユーザーが「この端末へ再取得」または「このパスを同期対象外にする」を選んだ場合のみ処理する。

## 1.7 baselineがない場合の判定表

| ID | L | R | 動作 |
|---|---|---|---|
| IN-01 | 不在 | 不在 | 何もしない |
| IN-02 | あり | 不在 | 新規Upload候補 |
| IN-03 | 不在 | あり | 新規Download候補 |
| IN-04 | あり | 同じ内容 | 同一として登録 |
| IN-05 | あり | 違う内容 | 初回競合。日時で勝者を決めない |
| IN-06 | あり | TOMBSTONE | 古いコピーか新規作成か判別不能。停止し復旧選択へ |
| IN-07 | 不在 | TOMBSTONE | 不在を維持。ローカルファイルを作らない |

IN-06/07を読む機能は0.3のみに実装する。既知のbaselineが壊れた場合に、勝手に「baselineなし」の表へ切り替えることは禁止する。

## 1.8 同期実行の状態機械

```text
IDLE
  -> PREFLIGHT
  -> RECOVER_PENDING（未完了処理がある場合）
  -> SCAN_LOCAL
  -> READ_REMOTE_SNAPSHOT
  -> PLAN
  -> PREVIEW / BLOCKED
  -> PREPARE_RECOVERY
  -> STAGE_REMOTE_OBJECTS
  -> COMMIT_REMOTE_HEAD（Upload等のRemote変更がある場合）
  -> APPLY_LOCAL
  -> VERIFY
  -> SAVE_BASELINES
  -> COMPLETED / PARTIAL / NEEDS_REVIEW
```

- 同一端末・同一Vaultでは同期を一つだけ実行する。再押下は二重実行せず状態表示を開く。
- MVP 0.1では既知の競合、読めない対象、パス衝突、未解決の不在候補があれば、通常同期全体を転送前に停止する。`blockedPaths`が空でない計画は実行しない。明示的に設定済みの対象外ファイルは、削除候補ではなく対象外として報告する。
- Localへの変更は、必要なRemoteの確定と復旧準備の後に行う。
- **Remoteの一回の公開更新と、各端末のファイル更新は別の確定点である。全端末一括のトランザクションではない。**
- Remote更新なしのDownload専用計画では、headの新規書き込みをしない。
- Remoteを公開済みでLocal適用に失敗した場合、Remoteを自動的に巻き戻さない。第8章で再照合する。

## 1.9 同期計画の不変条件

`SyncPlan`は、headのETag・commitId、対象ファイルのハッシュ、設定ハッシュ、baseline世代を含む。

プレビュー後にこれらが変われば、その承認は無効とする。
実行時に古い計画を流用しない。再生成した計画に破壊的操作があれば再承認を求める。

単なる全体スキャンの開始時点から、全ファイルの状態が凍結しているとは仮定しない。ローカル書き込みはファイルごとに直前条件を確認する。

## 1.10 名前変更・移動の扱い

MVP 0.1ではパス変更を「新パスの追加」と「旧パスの不在」として観測する。自動で同一ファイルと断定せず、旧パスにST-06を適用する。

MVP 0.2ではObsidianのイベントと内容の一致を手がかりに候補を表示する。ただしハッシュが同じという理由だけで名前変更を確定しない。旧パスの削除同期はしない。

MVP 0.3では、ユーザーが承認した新パスの公開と旧パスのtombstoneを一つのmanifest更新に含める。端末内の実ファイルの移動は別処理であり、途中終了から再開できるよう記録する。
リンク本文の自動書き換えは同期エンジンの仕事に含めない。

# 2. Safety Invariantsの具体条件

## 2.1 承認済みSIの具体化

| 規則 | 必須条件 | 不成立時 | 受入試験 |
|---|---|---|---|
| SI-001 | 必要なRemote情報を最後まで正常取得し、構造と参照を検証する | Local削除ゼロ。通常書き込みを開始しない | AT-09、AT-10 |
| SI-002 | 削除にbaselineの証拠と明示的な削除記録/承認がある | 不在を保留し削除しない | AT-11、AT-23 |
| SI-003 | 双方が違う内容へ変化していない | 競合として停止。自動で片方を選ばない | AT-04、AT-05 |
| SI-004 | 削除件数・割合・承認対象が安全条件内 | 自動処理禁止。個別の再確認を要求 | AT-24、AT-25 |
| SI-005 | パス、本文、形式、認証、実行状態が確定している | `BLOCKED`または`NEEDS_REVIEW` | AT-09、AT-15 |
| SI-006 | 変更予定・復旧参照を永続化し、操作結果を記録できる | 該当変更の前に停止 | AT-16、AT-17 |
| SI-007 | 新端末の不在を既存Remote削除の証拠にしない | 初回取り込みとして扱う | AT-06 |
| SI-008 | 新機能も上記の試験に合格する | 機能を無効のままにする | AT-31、AT-32 |

ここでいうRemote情報の「完全」とは、同一commitのmanifest全体と、その計画の判断・反映に必要な本文の取得が完了していること。R2の複数回のLISTを一時点のスナップショットと見なすことではない。

## 2.2 追加する実装規則

| ID | 規則 |
|---|---|
| SG-001 | Remoteの状態公開はheadへの条件付きPUT以外で行わない |
| SG-002 | 成功の応答がないPUTを、失敗したと決めつけない |
| SG-003 | ローカル上書き前に旧内容を復旧領域へ保存し、読み戻して検証する |
| SG-004 | ローカル本文が計画時点から変わっていれば、その計画で上書きしない |
| SG-005 | 通信・保存エラー時にbaselineを一括更新しない |
| SG-006 | 設定の除外、容量上限、読み取り失敗を削除扱いしない |
| SG-007 | JSONのパス・オブジェクトキーを信用せず、Vault外への参照を拒否する |
| SG-008 | 旧形式・未対応機能があるRemoteを無条件に上書きしない |
| SG-009 | 復旧用の本文とtombstoneを通常同期で物理削除しない |
| SG-010 | ログ・共有用診断に本文、秘密鍵、認証ヘッダーを含めない |
| SG-011 | MVP 0.1/0.2に削除伝播の実行経路を持たせない |
| SG-012 | 同じVaultへiCloud等の別同期を重ねる運用を正式サポートしない |

## 2.3 上書きと復旧用コピー

ローカルの既存Markdownを変更する場合、次の順序を守る。

1. 計画が期待する旧本文を読み、ハッシュとバイト長を確認する。
2. 本プラグインの`.svsync-recovery/`へ旧本文と復旧レシートを保存する。
3. 保存した本文を読み戻し、ハッシュとバイト長を照合する。
4. 操作ジャーナルに`RECOVERY_READY`を記録する。
5. `Vault.process()`の同期コールバックで、現在本文が期待する旧本文と完全一致するか確認する。
6. 一致する場合だけ、新本文を返す。一致しなければ例外で中止する。
7. 変更後に再読込し、想定内容を検証してからbaselineを更新する。

Obsidian公式は`Vault.process()`による読み取りと書き込みの間の保護、および非同期準備の後にコールバック内で旧内容を照合する方法を説明している。[S3]
この保証を、外部エディタやOSの同期ソフトまで含む排他制御と拡大解釈しない。

書き込み直後に別の変更が観測された場合は、その新しい内容を再度上書きしてはならない。結果を`LOCAL_CHANGED_AFTER_APPLY`として保留し、旧版・予定新版・現在版を保存したうえで再照合する。

MVP 0.1は対象ノートがこの端末のエディタで開かれている場合、受信による既存パス更新を延期する。全タブを閉じても外部書き込みまで防げるわけではなく、最終照合は省略しない。

## 2.4 ローカル作成

新規作成は、既存ファイルを上書きしない公開API経由で行う。`存在確認 -> 無条件write`だけで実装しない。
保存先が直前に作られた場合、`E_LOCAL_PATH_OCCUPIED`として再計画する。

`Vault.create()`を第一候補とするが、Windows/iPhone両方で同名・別ケース名の競合試験に合格させる。未検証の低レベルAPIへ勝手にフォールバックしない。

## 2.5 復旧領域の境界

- `.svsync-recovery/`はプラグイン本体のインストール先と分け、プラグイン削除だけで消える設計にしない。
- 同期対象から常に除外する。ここにある本文は通常のノート一覧には公開しない。
- 本文は暗号化されていないため、ローカル端末上の機密データとして扱う。
- 同一ディスク上の復旧コピーは、端末故障・紛失・ランサムウェアに対する独立バックアップではない。
- 初期版では自動清掃をしない。容量が上限に達したら書き込みを停止する。
- 重要データを扱う公開段階では、別の保存先へのバックアップと復元確認を利用条件として案内する。

## 2.6 パスの安全性

Remoteから来たパスを、ファイル操作APIにそのまま渡さない。

1. Vaultルートからの相対パスだけ許可する。絶対パス、ドライブ指定、UNC、空要素、`.`、`..`、NUL・制御文字を拒否する。
2. 区切りは`/`とし、受信パス中の`\`を拒否する。Windows用のパスへはローカルAdapterだけが変換する。
3. JSON内のパスをURLデコードしない。例えば`%20.md`を勝手に別名へ変えない。
4. NFCによる比較用パスを使い、実際のローカルパスとの対応を保持する。正規化で複数ファイルが同じ名前になる場合は停止する。
5. Windowsで扱えない予約名、末尾の空白/ピリオド、禁止記号を検査する。自動改名せず解決を案内する。
6. 大文字小文字、Unicode表現等による衝突を事前検査する。比較用キーは保守的に`NFKC(path).toLowerCase()`を用い、実際の保存APIによる既存パス検査も行う。これを全OSのファイル名同値性を完全再現する規則とは説明しない。
7. 親フォルダが通常ファイルだった場合、シンボリックリンク等だった場合、内部領域を指す場合は停止する。
8. 初期の相対パス長上限はUTF-16コード単位で240。これは本製品の制限であり、OSの絶対パス制限を保証しない。実保存の可否も検査する。

`.obsidian`に限らず、ユーザーが変更した設定フォルダ名も`app.vault.configDir`から取得して保護する。

## 2.7 初期版の制限値

| 設定 | 設計上の初期値 | 超過時 |
|---|---:|---|
| 対象Markdown数 | 5,000件 | 同期全体を停止し上限を表示 |
| Markdown単体 | 2 MiB | 対象外として明示。既存同期対象なら保留 |
| 現在の対象本文の合計 | 200 MiB | 書き込みを開始しない |
| manifestの最大サイズ | 16 MiB | 取得・解析・書き込みを停止 |
| head / commitの最大サイズ | 各64 KiB | メタデータ異常として停止 |
| JSONの最大ネスト | 16段 | 解析拒否 |
| 1回の計画の操作数 | 5,000件 | 計画を自動分割せず停止 |
| 本文・メタデータ通信の同時実行 | 合計2本まで | キューで待機 |
| ローカル変更の同時実行 | 1本 | 直列化 |
| 復旧領域のアプリ管理上限 | 512 MiB | 自動削除せず停止 |
| 不確定commitの祖先追跡 | 128世代まで | 結果不明として停止 |

1 MiBは1,048,576バイトとして計算する。受信サイズは宣言値だけでなく実際の長さも確認する。
これらは小規模なテスト用の安全上限であり、「この範囲なら必ず高速・安全」という保証ではない。

# 3. 初回同期

## 3.1 初期接続ウィザード

初回は必ずウィザードを通し、設定保存だけで同期を開始しない。

| ステップ | 入力・確認 | 書き込み可否 |
|---|---|---|
| 1. 用途確認 | テスト用Vault、独立バックアップ、別同期との重複がないこと | 不可 |
| 2. R2接続設定 | endpoint、bucket、接続先Vault ID、認証情報 | 不可 |
| 3. 接続検査 | 読み取り権限・形式・接続先の識別 | 原則読み取りのみ |
| 4. 能力検査 | 明示許可した専用probeで条件付きPUT等を確認 | probe領域だけ可 |
| 5. 運用選択 | 新しいRemoteを作る／既存Remoteに参加する | まだ不可 |
| 6. 比較 | 対象、除外、競合、必要容量、予定通信量 | 不可 |
| 7. 承認 | 具体的な計画と接続先を確認 | 承認した計画だけ可 |
| 8. 実行・検証 | 第1章の状態機械で実行 | 条件付き |

ウィザードのキャンセルはノートを変更しない。probeとして保存した小さな検査オブジェクトが残る場合は明示する。

## 3.2 iCloud上の既存Vaultを変更しない

開発・試験では、現在のiCloud Vaultを移動・書き換え・削除しない。
必要なサンプルだけを、別のローカルテストVaultへコピーして使用する。
iPhone側もiCloud上の既存Vaultではなく、この端末内の別テストVaultを使う。

プラグインは既知のクラウド同期パスや他の同期プラグインを可能な範囲で検知して警告・停止する。ただしすべての同期機構を自動検知できるとは主張しない。ユーザーの確認も必須とする。
将来のiCloud安全モードと本R2同期モードを同じVaultで同時に実行する設計にはしない。

## 3.3 新しいRemoteの作成

**BOOT-001** 新規作成ではランダムな`vaultId`と`epochId`を生成する。表示上のVault名だけで同一性を判断しない。
Remote prefixは原則`svsync/v1/<vaultId>/`とする。別製品が利用しているprefixは選べない。

手順：

1. 対象prefixを全ページ列挙し、未知の既存オブジェクトがないことを確認する。
2. `head.json`が認証付きGETで存在しないことを確認する。403、接続失敗、解析エラーを404に変換しない。
3. まず空のmanifestと初期commitを不変オブジェクトとして保存・読み戻し検証する。
4. `head.json`を`If-None-Match: *`付きで作成する。
5. 412なら他の初期化が先行した可能性がある。上書きせずheadを読み、既存Remote参加手順へ戻る。
6. headの確定を確認した後、ローカルの新規ファイルを通常の追加計画で取り込む。

途中で終了してmanifestだけが残った場合、当該端末の初期化ジャーナルで同じ試行だと確認できるものだけ再開する。由来不明の残骸を「空」とみなして初期化しない。

この処理の安全性はLISTによる排他に依存しない。最終的な作成競合はheadの条件付きPUTで防ぐ。

## 3.4 既存Remoteへの参加

参加情報にはendpoint、bucket、prefix、vaultId、epochId、形式識別子を含める。Secret Access Keyは参加情報やQRコードに含めない。

1. head、commit、manifestを取得し、それぞれの識別子とハッシュの対応を検証する。
2. 表示名ではなくvaultId・epochIdが参加情報と一致することを確認する。
3. この端末では新しいdeviceIdを生成する。別端末のbaselineやpending journalは取り込まない。
4. 空Vaultなら原則Downloadのみ。Remoteを削除する計画は生成しない。
5. 非空Vaultなら第1.7節の初回比較表を用いる。
6. 同名・別内容は初回競合として止める。Local優先・Remote優先の一括上書きは初期版に用意しない。
7. ファイルごとに反映と内容確認が完了したものだけbaselineへ記録する。

## 3.5 Remoteが消えた・接続設定が変わった場合

一度接続したRemoteのheadが404になっても、新規作成扱いに戻さない。`E_REMOTE_HEAD_MISSING`で停止する。

endpoint、bucket、prefix、vaultId、epochIdのいずれかが変わる設定保存では、通常同期を停止して再接続ウィザードへ戻す。既存baselineを別接続先へ流用しない。
「Remoteの再初期化」「全データの強制送信」は通常設定画面に置かない。別途、バックアップと移行手順を伴う管理操作とする。

## 3.6 再インストール・メタデータ消失

ローカルbaselineが破損した場合は自動初期化しない。
正常な複数世代のローカル状態とジャーナルから復元できなければ、`REBASE_REQUIRED`で停止する。

ユーザーが明示的に再参加を選ぶときは、現在のLocalとRemoteをともに保存したうえで「baselineなし」の比較を行う。以前の削除承認・保留中の操作は引き継がない。

## 3.7 Remotely Saveからの移行

初期移行方法は次に限定する。

```text
元の同期を停止
  -> 元Vaultと元Remoteを別途保全
  -> 各端末に未同期の変更がないか確認
  -> 合意したローカルコピーをテスト用に複製
  -> 新prefixで初回同期
  -> 別テスト端末で内容を検証
```

旧プラグインと新プラグインを同じRemote領域に同時接続しない。
旧Remoteの独自メタデータや暗号化データを直接読み替えるインポーターは本書では実装しない。

**MVP段階は「インストールを入れ替えれば既存Remoteのまま移行完了」という製品ではない。** この制限をREADMEと移行画面の両方に記載する。

# 4. 競合

## 4.1 競合の種類

| ID | 状況 | 自動判断 |
|---|---|---|
| CF-01 | 同一パスのLocalとRemoteがbaselineから別内容へ変更 | 勝者を決めない |
| CF-02 | 初回参加で同名・別内容 | 勝者を決めない |
| CF-03 | 一方が削除候補、他方が編集 | 削除しない |
| CF-04 | Remoteのtombstoneに対してLocalに未反映の編集 | 削除も復活の公開も自動でしない |
| CF-05 | ケース・Unicode・ファイル/フォルダのパス衝突 | 自動改名しない |
| CF-06 | 実行直前にLocalが変更 | 旧計画の上書きを禁止 |
| CF-07 | head更新時の412 | 同時更新として再読込。内容比較してから競合か判定 |

**412それ自体は「同じノートの競合」とは限らない。別のノートの変更なら、新しいmanifestに再適用できる。**

## 4.2 MVP 0.1の競合処理

競合対象、種類、Local/Remoteの内容が異なること、前回共通版の有無を表示して停止する。
本文の自動マージ、時刻による選択、容量が大きい方の採用は行わない。

ユーザーは別名コピーを作成して退避したうえで手動整理できるが、プラグインが証拠なく「解決済み」と扱ってはならない。次回走査で内容一致を確認する。
競合に関係のないファイルだけ続行する部分同期UIは0.1の範囲外とする。

## 4.3 MVP 0.2の「両方残す」操作

デフォルトは停止であり、ユーザーが具体的なプレビューを承認したときにだけ実行する。

原則の結果は次のとおり。

- 元のパスには、確認時のRemote版を残す。
- Local版を別パスへ保存する。
- どちらが正しいかをプラグインが決めたわけではないと表示する。
- 復旧用コピーと履歴も保持する。

元パスをRemote版にするのは、確認画面で明示する保存方法である。時刻による優先ルールではない。

手順：

1. L/R/Bとheadの内容を確定し、Local版・Remote版の本文を検証する。
2. Local版を復旧領域に保存する。
3. 別名ノートを非上書きで作成し、内容を検証する。
4. 元パスのRemote版と、別名パスのLocal版の両方を含むmanifestを作成する。
5. headをCASで更新する。412なら承認対象を再照合する。
6. Remoteで両方の参照が公開された後に、元のLocalパスを条件付きでRemote版へ置換する。
7. 成功したパスだけbaselineを進める。

途中終了ではコピーが余分に残っても構わない。コピーを減らすために未確認データを削除しない。

## 4.4 競合コピーの命名と重複防止

競合グループの識別子は次で定義する。

```text
conflictId = SHA-256(
  UTF8(JSON.stringify([
    "conflict-v1",
    vaultId,
    canonicalPath,
    baselineHashOrNull,
    sort([localHash, remoteHash])
  ]))
)
```

自動生成する保存先は次を標準とする。

```text
_SyncConflicts/<conflictId>/<localHash>.md
```

生成ノートの本文には勝手にヘッダー・説明文を追加しない。元ノートのバイト列をそのまま保存する。
元パスと競合理由の対応はメタデータとUIで表示する。

同じパス・同じ内容がすでにあれば再利用する。既存の競合コピーがユーザーによって編集されていたら上書きせず、新しいUUIDを加えた別名へ保存する。
生成された競合コピーも通常の同期対象とするが、当該実行が作成したノートとしてbaselineを登録し、同じ実行で無限にコピーを生成しない。

## 4.5 「Localを採用」「Remoteを採用」の扱い

一方のみを採用する操作でも、失われる側の本文を復旧領域とRemoteの不変blobに保持する。
プレビューには「通常ノートとしては片方を採用する」「他方は復旧用に残る」を区別して表示する。

この操作は0.2の追加機能とし、MVP 0.1には付けない。
ユーザーが片方を選択した後でも、実行時のLocalハッシュまたはheadが変わった場合は承認を無効化する。

## 4.6 バイナリ添付

MVP 0.2では新規の添付ファイルと別名コピーを扱う。初期上限は1ファイル10 MiB、単発GET/PUTのみとし、multipartは実装しない。

既存バイナリのローカル置換について、Markdownの`Vault.process()`と同じ保護があるとは仮定しない。
条件付き置換と復旧の実機試験に合格するまでは、元パスを更新せず別名保存または保留とする。この制限がある間は「添付の完全な自動更新」に対応したと表示しない。

画像・PDF等の自動マージは行わない。

# 5. 削除

## 5.1 段階と用語

| 用語 | 本書での意味 |
|---|---|
| 不在 | ファイルが見つからないという観測 |
| 削除候補 | baselineにあったものが不在になった等、ユーザー確認が必要な状態 |
| 論理削除 | manifestにtombstoneを記録し、通常ノートとして扱わなくすること |
| ローカル退避 | 本文を復旧領域へ移し、通常のパスから外すこと |
| 物理削除 | 本文や履歴をストレージから消すこと |

MVP 0.1/0.2は削除伝播を禁止する。
MVP 0.3で実装するのは、**明示確認付きの論理削除とローカル退避**である。
R2上のblob、manifest、commit、tombstoneの物理削除は、0.3でも実装しない。

## 5.2 削除機能の有効化条件

次のすべてが必要。

1. 全接続端末が`tombstones-v1`を解釈できることをユーザーが確認する。
2. Remoteの`requiredCapabilities`に`tombstones-v1`を追加する形式更新を承認する。
3. 旧クライアントがこの機能を見て書き込みを拒否する試験に合格している。
4. 削除、編集競合、オフライン端末、途中終了、退避失敗の受入テストに合格している。
5. `deletePropagationEnabled`を明示的に有効化する。初期値は`false`。

機能を有効化しても、MVP 0.3では削除に関する実行を自動承認しない。削除元の公開と削除先端末の退避は、それぞれの具体的な計画の確認を必要とする。

## 5.3 削除候補の検出

ローカルの不在だけではtombstoneを作成しない。
baseline、完全走査、対象外設定、読み取りエラーの有無を確認し、UIに候補として並べる。

Obsidianの削除イベントは候補作成の手がかりであり、端末間削除の自動承認にはしない。
端末がオフラインの間に消えたファイルも、次回接続時に同じ確認手順を通す。

## 5.4 tombstoneの公開

ローカル不在を起点とする場合の必須条件：

- baselineがLive版を記録している。
- 現在RemoteのLive版がそのbaselineと同一である。別内容なら削除対編集の競合にする。
- 削除対象の本文blobを取得・検証でき、復旧可能である。
- 削除対象、件数、接続先をユーザーが確認している。
- headのETag、manifestの参照、承認した操作集合が変わっていない。

tombstoneには、削除前のrevisionId、内容参照、承認操作ID、削除を公開したdeviceIdを残す。
削除時刻は表示用であり、古い編集を破棄する根拠には使わない。

## 5.5 tombstoneを受信した端末の状態表

| baseline | Local | 動作 |
|---|---|---|
| 削除前のLive版を確認済み | そのままの内容 | 確認後、復旧領域へ退避できる |
| 削除前のLive版を確認済み | 別内容へ編集済み | 削除対編集の競合。退避による非表示も自動ではしない |
| 削除前のLive版を確認済み | 不在 | 追加の削除不要。tombstoneを確認済みにできる |
| 共通版なし | ファイルあり | 古いコピーか新規作成か不明。停止して選択を求める |
| 共通版なし | 不在 | 不在を維持。確認済みtombstoneをbaselineへ登録 |
| 削除済みbaseline | 新しい内容がある | 自動復活しない。明示的な復元か別名保存を選ぶ |

「30日経ったのでtombstoneを消す」といった期限だけの清掃は行わない。長期間オフラインだった端末から古いファイルが戻る問題を避けるため、墓標は形式移行/GC仕様が完成するまで保持する。

## 5.6 ローカル退避手順

`Vault.delete()`による永久削除は使用しない。
本プラグインが追跡できる一意な復旧先へ移し、レシートを保存する方式を採用案とする。

1. 対象が開いている場合は処理を延期する。
2. 現在の本文を読み、承認時のハッシュと一致するか確認する。
3. 先に別の復旧コピーを作成し、読み戻して検証する。
4. 操作ジャーナルを永続化する。
5. 非上書きの一意な退避先へ対象を移す。
6. 移した実物を再読込し、想定内容との一致を確認する。
7. 一致した場合にのみ、その端末の削除反映を完了と記録する。

**一般的なファイル移動APIに、内容ハッシュを条件にした原子的な移動があるとは仮定しない。**
手順中に別内容になっていた場合、退避先の新しい内容も保持する。元パスが空いていれば非上書きで復元し、占有されていれば両方を残して`DELETE_EDIT_RACE`として止める。

隠し復旧フォルダへの移動、衝突時の非上書き、アプリ終了時の挙動をWindows/iPhoneで確認できない限り、ローカル退避機能を有効にしない。
フォルダの再帰削除は行わず、対象ファイルごとに扱う。空になった通常フォルダを自動削除しない。

## 5.7 大量削除ガード

対象端末内の退避計画と、Remoteのtombstone公開計画でそれぞれ判定する。

- `D`：その計画で通常表示から外れるファイルの重複を除いた件数。
- `N`：その保存先で、計画開始前に同期対象としてLiveだったファイル件数。
- 設定変更による除外は削除件数に含めず、削除そのものを実行しない。

```text
massDelete =
  D >= 100
  OR (D >= 5 AND D / max(N, 1) >= 0.10)

allDelete = D > 0 AND D >= N
```

`massDelete`または`allDelete`なら、自動実行は禁止する。
通常の確認に加えて対象一覧、復旧先の検証結果、独立バックアップの確認を表示し、接続先Vault IDの末尾を入力する追加確認を求める。

少数削除でもMVP 0.3では通常の明示確認が必要である。「しきい値未満なら安全」とは表示しない。
計画を分割してしきい値をすり抜けない。評価は一つのユーザー操作から作られた計画全体に適用し、リトライ時にも承認済みの集合を保持する。

### 境界値の試験例

以下は上記の式から計算した試験入力と期待値である。falseでも通常の削除承認は省略しない。

| N | D | D/N | massDelete | allDelete |
|---:|---:|---:|---|---|
| 100 | 9 | 9.0% | false | false |
| 100 | 10 | 10.0% | true | false |
| 2,000 | 100 | 5.0% | true | false |
| 10 | 4 | 40.0% | false | false |
| 1 | 1 | 100.0% | false | true |
| 500 | 49 | 9.8% | false | false |
| 500 | 50 | 10.0% | true | false |

## 5.8 削除したノートの復元

復元は過去へ全体を巻き戻す操作ではなく、**過去の本文を使った新しいLive版の作成**である。

- 別名への復元をデフォルトとする。
- 元パスへの復元は、現在のtombstoneまたはLive版を再確認し、必要なら競合処理を行う。
- 元のtombstoneと復旧レシートは消さない。
- 既存の別内容を無条件に置き換えない。
- 復元用blobが欠損している場合、ノートの内容を推測して生成しない。

## 5.9 履歴と容量

MVP 0.1〜0.3ではRemoteの物理清掃を行わないため、現在のノート容量より使用量が大きくなる。
容量が増えたときは警告・書き込み停止・手動エクスポートを提供し、無料枠を守るために古い内容を勝手に削除しない。

将来のGCは、到達可能なblob、commitの祖先、tombstone、未完了処理、オフライン端末を考慮する別仕様とする。

# 6. R2 Backend

## 6.1 対応範囲と依存関係

初期の正式な検証対象はCloudflare R2 Standard、Windows版Obsidian、iPhone版Obsidianに限定する。
AWS S3、MinIO、WebDAV、OneDriveなどの互換性を本書では保証しない。

通信はR2のS3 APIへ直接行う。独自の中継サーバー、Cloudflare Workers、課金API、ユーザーアカウント用サーバーを必須にしない。

R2はS3 APIの全機能を実装しているわけではない。公式の互換表は、条件付きPutObject、GetObject、HeadObject、ListObjectsV2の対応を示している。[S1]
本書ではS3のバケットバージョニングや複数キー間トランザクションを前提にしない。

## 6.2 接続設定

| 項目 | 仕様 |
|---|---|
| `endpoint` | HTTPSのR2 S3エンドポイント。公開配信URLではない |
| `region` | `auto` |
| `bucket` | プラグイン専用の既存バケットを推奨 |
| `prefix` | `svsync/v1/<vaultId>/`を原則とする |
| `accessKeyId` | R2のS3認証用キー |
| `secretAccessKey` | 秘密値。共有設定・Remote・ログに出さない |
| `storageClass` | `STANDARD` |
| `vaultId` / `epochId` | 接続先の同一性を確認する識別子 |

初期リファレンス試験は通常の`<accountId>.r2.cloudflarestorage.com`で実施する。
地域別エンドポイントを使う場合も正しい対応先を明示設定し、個別試験完了前は「未検証」と表示する。R2の地域別バケットには対応するエンドポイントが必要である。[S6]

endpointに認証情報、任意のパス、query、fragmentを含めない。HTTPと公開`r2.dev`を拒否する。
リダイレクト先へ認証ヘッダーを転送しない。別ホストへの301/307等は設定確認のため停止する。

## 6.3 認証情報と権限

バケットを絞ったObject Read & Write相当の権限を使用する。バケット作成・削除・設定変更のAdmin権限をプラグインは要求しない。R2にはバケットを指定できるオブジェクト権限がある。[S6]

ただし「アプリがDeleteObjectを呼ばない」ことと「漏えいしたキーで削除できない」ことは別である。資格情報の権限を超えた安全性を説明しない。

初期設定は**セッション内のみ保存**とする。再起動時は再入力が必要となる。
永続保存を選べる場合は、実際の保管方式を警告する。OSのKeychain等を使用していないのに「安全に暗号化して保存」と表示してはならない。

通常のプラグイン設定に保存する実装を採用する場合、そのファイルは他のプラグイン・端末利用者から読み取られる可能性を明示し、設定エクスポートと同期から除外する。Secretは必ずマスク表示する。

## 6.4 モバイル互換の通信層

共有コードでNode.jsの`fs`、Electron、ネイティブ専用モジュールを前提にしない。Obsidian公式資料は、モバイルでNode.js/Electron APIが利用できない点を説明している。[S4][S5]

S3の署名処理にはライセンス確認済みの既存実装を利用する。独自に署名アルゴリズムを発明しない。
AWS SDK for JavaScript v3は候補とするが、依存関係とHTTP HandlerをWindows/iPhoneで検証してから採用する。[S7]

ネットワークは`R2Transport`で抽象化し、ObsidianのHTTP API等へのAdapterを用意する。必要な契約は次のとおり。

- HTTP status、レスポンスヘッダー、実際の本文バイト列が取得できる。
- エラー応答を空データへ変換しない。
- `If-Match`と`If-None-Match`を保持して署名・送信できる。
- ETagの引用符を含む値を壊さず扱える。
- バイナリとJSONのバイト列を変更しない。
- 通信中断の可否が明確である。中断できない通信を中断済みと扱わない。
- SDK内蔵のリトライとアプリのリトライが掛け算にならない。再試行は一つの層に集約する。

ブラウザ向けCORSの設定だけでモバイルで動くと判断しない。CORS問題を理由にバケットを公開したり、匿名書き込みを許可したりしない。

## 6.5 R2上の保存構造

```text
svsync/v1/<vaultId>/
  head.json
  commits/<commitId>.json
  manifests/<manifestSha256>.json
  blobs/<先頭2桁>/<storedSha256>

svsync-probes/<deviceId>/<probeId>/
  conditional-write-test
```

`head.json`以外は書き換えないという**アプリケーション側の規約**である。R2のWORM保護を適用済みという意味ではない。
本文blobのキーは内容由来で、manifestに通常のVaultパスとの対応を保存する。
R2上にそのまま人間が編集する`.md`ツリーを作る方式ではない。

手動閲覧・将来の離脱のため、manifestとblobからMarkdownツリーを復元できる形式と手順を公開する。初期版の移行試験には、少なくともローカルVaultから通常ファイルとして書き出せることと、Remoteの読み取り専用エクスポートの検証を含める。

## 6.6 不変オブジェクトの作成

blob、manifest、commitの作成は次で統一する。

1. キーと本文バイト列を決め、同じ再試行では変更しない。
2. `PutObject`に`If-None-Match: *`を付ける。
3. 成功時はGETで読み戻し、期待するSHA-256と長さを照合する。
4. 412なら既存オブジェクトをGETし、期待する内容なら重複保存済みとして扱う。
5. 412で内容が異なる場合はキー衝突・破損として停止する。上書きして修復しない。

本文の重複排除は同じVault内だけを対象とする。
保存直後の検証が終わっていないblobを、新しい公開manifestから参照してはならない。

## 6.7 Remoteスナップショットの取得

1. `head.json`を取得し、本文とETagを同じ応答から受け取る。
2. headが指すcommitを取得し、commitのハッシュを確認する。
3. commitが指すmanifestを取得し、manifestのハッシュを確認する。
4. vaultId、epochId、世代、必須機能、パス重複、サイズ上限を検証する。
5. 操作の判断・実行に必要なblobを取得・検証する。

Remoteの対象集合は、この不変manifestの集合とする。
R2の強い整合性があっても、複数回のLISTや複数ファイルの読み書き全体が一つの時点に固定されるとは仮定しない。[S2]

R2のS3 APIへ直接アクセスし、CDNの公開配信キャッシュを同期判定に使わない。公式資料もカスタムドメインのキャッシュとS3 APIのアクセスを区別している。[S2]

## 6.8 headの条件付き更新（CAS）

CASは「読んだ時点から変わっていない場合だけ、変更する」操作を意味する。

```text
旧head H0 とETag E0を読む
  -> 必要なblobを保存・検証
  -> 新しいmanifest M1を保存・検証
  -> parent=H0.commitIdのcommit C1を保存・検証
  -> 候補head H1をジャーナルに保存
  -> PUT head.json / If-Match: E0
```

- 既存headの更新には、取得時のETagをそのまま条件として使用する。
- 初回headの作成だけ`If-None-Match: *`を使用する。
- `If-Match`なしの既存head上書きは禁止する。
- 自作のロックファイルを「存在確認してから作る」だけの排他機構に置き換えない。
- 新manifestは最新のRemote全体に承認済み差分だけを適用する。対象外のパス・未変更のレコードを落とさない。

R2公式互換表はPutObjectの`If-Match`と`If-None-Match`対応を示している。[S1]
SDKの型や挙動が対応していない場合、条件を外して動作させることは禁止する。Adapterを修正して検証するか、書き込みを無効にする。

## 6.9 二端末の同時更新

例：PCとiPhoneが同じH0を読んだ後、別々の変更を公開しようとした場合。

- 最初の条件付きhead更新だけがH0に対して成功する。
- 後続は412を受け、最新headとmanifestを読み直す。
- 別ファイルの変更なら、最新manifestに自分の差分を再計画する。
- 同じファイルの別内容なら、第4章の競合にする。
- 再計画は連続3回までとし、再び競合したら`E_REMOTE_BUSY`で停止する。

古いmanifestを強制的に再送して他端末の変更を消すことは禁止する。
未公開のblob等が残っても、直ちに物理削除しない。

## 6.10 head更新の応答が失われた場合

タイムアウトは「更新失敗」の証拠ではない。`REMOTE_COMMIT_UNKNOWN`を記録し、Localの反映を止める。

次回確認時の分類：

| 観測 | 判定 |
|---|---|
| 最新headが自分のcommitIdを指す | 公開成功を確認 |
| 最新headの検証済み祖先に自分のcommitIdがある | 公開後に別更新があった。自分の公開は成功 |
| 最新headが試行前のcommitId・ETagのまま | 同一候補を同一CAS条件で再試行可能 |
| 別の枝が進み、自分のcommitIdが祖先にないと検証できた | 自分の公開は採用されていない。最新状態で再計画 |
| 祖先の欠損・ハッシュ不一致・128世代超過で判定不能 | 不明のまま停止。成功/失敗を推測しない |

祖先は`parentCommitId`と`parentCommitSha256`を照合してたどる。
「候補commitオブジェクトが存在する」だけでは、headに採用された証拠にならない。

R2の一つのhead更新が成功しても、全端末への反映が完了したことにはならない。UIは「Remote公開済み」と「この端末に反映済み」を分ける。

## 6.11 LISTの使い道とページング

ListObjectsV2は初期化確認、probe管理、容量診断、読み取り専用検査に使用する。本文同期の正式な一覧取得には使用しない。

- prefixを必ず指定する。
- `IsTruncated`がtrueの間は`NextContinuationToken`を引き継ぐ。
- tokenが欠ける・同じtokenが繰り返される・途中エラー・XML解析失敗なら不完全とする。
- 不完全な一覧を返すAPIを用意しない。成功時の完全結果か、明示的な失敗を返す。
- 途中ページまでの結果から削除・Remote初期化を判断しない。

## 6.12 クラウド費用の制御

無料枠内で試すことを目標とするが、無料を保証しない。
R2 Standardには保存容量と操作回数の無料枠があり、枠を超えると課金対象となる。無料枠はInfrequent Accessには適用されない。[S8]

本プロジェクトでは以下を実装する。

- 手動同期を初期値とし、意味のない高頻度ポーリングをしない。
- この端末が送ったGET/HEAD/PUT/LISTと実バイト数を数える。再試行・検証GETも含める。
- 推定保存量は現行本文だけでなく、blobの履歴、manifest、commit、未公開の残骸を含める。
- 1回の実行でAPI送信50,000回に達したら、新しい送信を止めて安全に中断する。
- 本製品の管理prefixの診断上のサイズが1 GiBに達したら、初期版の書き込みを停止する。ユーザーが明示的に上限を上げる場合は課金リスクを表示する。
- 費用上限に近づいたからといって、復旧データを自動削除しない。

保存量の診断はprefixの全ページ列挙で得たサイズを合計する。Strict予算ガードが有効な初期版では、直近の完全診断がない、または新しい計画の保守的な増分を加えると上限に達する場合に新規書き込みを停止する。診断中に別端末が書き込む可能性もあるため、これを正確な課金上限とは扱わない。

端末のカウンターはCloudflareの請求額の確定値ではない。他端末、他バケット、別アプリの利用まで網羅できない。
**アプリの停止しきい値は、Cloudflareアカウント全体の強制課金上限ではない。** 管理画面での利用量確認が必要である。

## 6.13 使用する操作・禁止する操作

| 区分 | 操作 |
|---|---|
| 初期に使用 | GetObject、必要時のHeadObject、PutObject、ListObjectsV2 |
| 通常同期で使用しない | DeleteObject、DeleteObjects、CopyObject、multipart操作 |
| 実装しない | バケット作成/削除、公開設定の変更、Lifecycle設定変更 |

Backendの公開インターフェースに物理削除メソッドを持たせない。
テストではHTTPメソッドとS3コマンドを監視し、通常同期に削除APIが含まれないことを確認する。

# 7. メタデータ

## 7.1 共通形式

メタデータはUTF-8のJSONとし、バージョンを必ず持つ。
本書の文書バージョン`0.1`、プラグインのMVPバージョン、Remoteの`protocolMajor`は別の値である。

識別子は暗号学的な乱数から生成したUUID v4を基本とする。`Math.random()`へフォールバックしない。
SHA-256は小文字の64桁16進文字列を使用する。
整数は非負のJavaScript安全整数に制限し、浮動小数点を世代・件数・サイズに使わない。
日時はUTCのISO 8601文字列で記録するが、競合解消や削除の新旧判断に使用しない。

### 正規化JSON

RemoteのJSONは次の決定的なシリアライズ規則を使用する。

- オブジェクトのキーをUTF-16コード単位の辞書順に並べる。
- 配列順は保持する。ただし`entries`はcanonicalPath順、`requiredCapabilities`は文字列順にしてから出力する。
- 数値は許可された整数だけ、文字列はJSON標準のエスケープを使用する。
- 空白・インデント・BOM・末尾改行を付加しない。
- 未定義値、NaN、Infinityを拒否する。

受信時はJSONを解析・スキーマ検証し、この規則で再出力したバイト列と元のバイト列が一致することを確認する。これにより重複キー等を含む非正規表現も拒否する。
本文blobにはこのJSON正規化を適用しない。

## 7.2 型定義：Remote

以下は**契約を示すTypeScript型**であり、そのまま完成プラグインになるコードではない。すべての受信JSONに実行時検証が必要である。

```typescript
type UUID = string;
type Sha256 = string;
type CanonicalPath = string;

type Capability =
  | "manifest-v1"
  | "identity-content-v1"
  | "attachments-v1"
  | "conflict-copy-v1"
  | "tombstones-v1";

interface ContentRef {
  transform: "identity";
  plainSha256: Sha256;
  storedSha256: Sha256;
  plainSize: number;
  storedSize: number;
  mediaType: "text/markdown" | "application/octet-stream";
}

interface ConflictOrigin {
  conflictId: Sha256;
  originalPath: CanonicalPath;
  baselineSha256: Sha256 | null;
  localSha256: Sha256;
  remoteSha256: Sha256;
}

interface LiveEntry {
  state: "live";
  path: CanonicalPath;
  revisionId: UUID;
  parentRevisionId: UUID | null;
  content: ContentRef;
  modifiedByDeviceId: UUID;
  modifiedAtUtc: string;
  conflictOrigin: ConflictOrigin | null;
}

interface TombstoneEntry {
  state: "deleted";
  path: CanonicalPath;
  revisionId: UUID;
  parentRevisionId: UUID;
  deletedFromRevisionId: UUID;
  deletedFromContent: ContentRef;
  deleteOperationId: UUID;
  deletedByDeviceId: UUID;
  deletedAtUtc: string;
}

type ManifestEntry = LiveEntry | TombstoneEntry;

interface Manifest {
  format: "svsync-manifest";
  schemaVersion: 1;
  protocolMajor: 1;
  vaultId: UUID;
  epochId: UUID;
  generation: number;
  requiredCapabilities: Capability[];
  entries: ManifestEntry[];
}

interface Commit {
  format: "svsync-commit";
  schemaVersion: 1;
  vaultId: UUID;
  epochId: UUID;
  generation: number;
  commitId: UUID;
  parentCommitId: UUID | null;
  parentCommitSha256: Sha256 | null;
  manifestSha256: Sha256;
  planId: UUID;
  planDigest: Sha256;
  operationCount: number;
  createdByDeviceId: UUID;
  createdAtUtc: string;
}

interface Head {
  format: "svsync-head";
  schemaVersion: 1;
  protocolMajor: 1;
  vaultId: UUID;
  epochId: UUID;
  generation: number;
  commitId: UUID;
  commitSha256: Sha256;
  manifestSha256: Sha256;
  requiredCapabilities: Capability[];
}
```

初期版では`transform=identity`のみ許可し、`plainSha256=storedSha256`、`plainSize=storedSize`を検証する。
将来の暗号化では必須capabilityと形式を更新する。後から暗号化したデータを旧クライアントが平文として扱わないようにする。

## 7.3 Remoteレコードの整合規則

**META-001** head、commit、manifestのvaultId・epochId・generationを一致させる。

**META-002** 初期世代は0、親commitはnull。通常更新は親のgenerationから1増加する。世代を巻き戻す通常操作はない。

**META-003** headの`commitSha256`はcommitの保存バイト列のハッシュ、`manifestSha256`はmanifestの保存バイト列のハッシュと一致しなければならない。

**META-004** LiveEntryが指すblobキーは`storedSha256`から導出する。Remoteから任意のURLや別バケットを参照させない。

**META-005** LiveEntryの内容を変更したら新しいrevisionIdを生成する。同じ内容の一致確認だけでは新revisionを発行しない。

**META-006** 同一canonicalPathのレコードは一つだけとする。Liveとtombstoneを同じパスで同時に持たない。

**META-007** tombstoneには削除前の本文参照を必ず残す。tombstoneを消してパスを完全不在にする更新は禁止する。

**META-008** 未対応の必須capabilityがあれば、本文・Remote・baselineの変更を停止する。エラー表示のための読み取りだけ許可する。

**META-009** manifestはLiveとtombstoneを合わせて最大10,000レコード、かつ16 MiB以下。超過時にtombstoneを自動間引きしない。

**META-010** 一度観測した世代より古いhead、同世代で別commitのheadを受信したら`E_REMOTE_HISTORY_CHANGED`で停止する。
これだけで悪意あるRemote改ざんを完全検出できるとは主張しない。

## 7.4 ローカル保存構造

```text
<Vault>/
  .svsync-state/
    identity.json
    settings-public.json
    checkpoint-a.json
    checkpoint-b.json
    journal/<runId>/<sequence>-<eventId>.json
    pending/<planId>.json
  .svsync-recovery/
    blobs/<sha256>
    receipts/<operationId>.json
    quarantine/<operationId>/<fileName>
```

すべて同期対象外とする。プラグインの通常アンインストール処理で自動削除しない。

`settings-public.json`には秘密鍵を含めない。
秘密値の保存先は第6.3節に従い、初期値はメモリのみとする。

deviceIdとinstallationIdは表示用の端末名から作らない。
Vaultを別端末へ丸ごとコピーした場合にidentityやbaselineを共有しないよう、Vault外のアプリ固有ストレージにあるinstallationIdと照合する。利用する保存APIはモバイル検証で確定する。
照合ができない場合は端末再登録として停止し、古い未完了操作を引き継がない。

## 7.5 baselineの型

```typescript
interface LiveBaseline {
  state: "live";
  path: CanonicalPath;
  revisionId: UUID;
  plainSha256: Sha256;
  plainSize: number;
  commonCommitId: UUID;
  verifiedAtUtc: string;
}

interface DeletedBaseline {
  state: "deleted";
  path: CanonicalPath;
  tombstoneRevisionId: UUID;
  deletedFromSha256: Sha256;
  commonCommitId: UUID;
  verifiedAtUtc: string;
}

type BaselineEntry = LiveBaseline | DeletedBaseline;

interface LocalCheckpointPayload {
  vaultId: UUID;
  epochId: UUID;
  installationId: UUID;
  deviceId: UUID;
  sequence: number;
  maxObservedRemoteGeneration: number;
  lastObservedRemoteCommitId: UUID;
  lastAppliedJournalSequence: number;
  settingsDigest: Sha256;
  baselines: BaselineEntry[];
}

  format: "svsync-checkpoint";

```

baselineは端末ごとに異なる。Remoteに置く共有baselineは作らない。
同じパスでもPCが世代10、iPhoneが世代7を最後に確認している状態は正常である。

## 7.6 チェックポイント更新

- checkpoint-a/bを交互に保存し、既存の正常な一方を残す。
- 新しいpayloadのハッシュを含め、書き込み後に読み戻して検証する。
- 起動時は有効なチェックポイントのうちsequenceが大きい方を選ぶ。
- 片方が壊れている場合は、古い正常版と未完了ジャーナルを再照合する。
- 両方が壊れている場合は空のbaselineを作らず停止する。
- ローカルストレージAPIの読み戻し成功を、突然の電源喪失に対する完全な永続性保証と説明しない。

baselineを進める条件は次のいずれか。

| 操作 | 条件 |
|---|---|
| Upload | Remoteのcommit確定を確認し、送信したLocal内容との対応が取れる |
| Download | Local保存・読み戻しが想定内容と一致する |
| 同内容の一致確認 | Localの実読込とRemoteの検証済み内容参照が同じ |
| 削除 | 0.3でtombstoneを確認し、必要なLocal退避が完了するか既に不在 |

Localがその間に変わっていた場合、現在の内容を無視して「同期済み」にしない。
安全に共通版を特定できるまでは該当パスのbaselineを保留する。
同期全体に一件でも失敗があったという理由で、すでに確認済みの別パスのbaselineまで無条件に消去しない。

## 7.7 同期計画の型

```typescript
type OperationKind =
  | "UPLOAD_NEW"
  | "UPLOAD_UPDATE"
  | "DOWNLOAD_NEW"
  | "DOWNLOAD_UPDATE"
  | "CONFIRM_EQUAL"
  | "PRESERVE_CONFLICT"
  | "PUBLISH_TOMBSTONE"
  | "QUARANTINE_LOCAL";

interface PlannedOperation {
  operationId: UUID;
  kind: OperationKind;
  path: CanonicalPath;
  expectedLocalSha256: Sha256 | null;
  expectedRemoteRevisionId: UUID | null;
  desiredContent: ContentRef | null;
  recoveryRequired: boolean;
  userApprovalRequired: boolean;
}

interface SyncPlan {
  format: "svsync-plan";
  schemaVersion: 1;
  planId: UUID;
  runId: UUID;
  vaultId: UUID;
  epochId: UUID;
  deviceId: UUID;
  baseRemoteCommitId: UUID;
  baseRemoteEtag: string;
  baseCheckpointSequence: number;
  settingsDigest: Sha256;
  operations: PlannedOperation[];
  blockedPaths: CanonicalPath[];
  proposedCommitId: UUID | null;
  estimatedUploadBytes: number;
  estimatedDownloadBytes: number;
  approvedPlanDigest: Sha256 | null;
  createdAtUtc: string;
}
```

`expectedLocalSha256=null`は「作成前に不在である必要がある」を意味する。読み取り失敗の代用にしてはならない。
Remoteへの新規作成と更新を区別する。`UPLOAD_UPDATE`には既存revisionの証拠が必要である。

`recoveryRequired`や`userApprovalRequired`はUIから自由指定させず、OperationKindと現状からPlanner/Safety層が算出する。Executorも規則を再検査し、falseに書き換えることで安全機能を迂回できないようにする。

`PRESERVE_CONFLICT`は複合操作であり、実行前に別名の作成・公開・元パスの条件付き更新の下位操作へ展開して、保存先とoperationIdをpending planに固定する。実行途中で別名を再抽選しない。

`approvedPlanDigest`は、そのフィールド自体をnullにした計画の正規化JSONのハッシュとする。
再計画時は、以前のdigestに対するユーザー承認を引き継がない。

## 7.8 ジャーナル

操作イベントを追記専用の別ファイルとして保存する。イベントごとにsequence、前イベントのハッシュ、payloadのハッシュを持たせる。
ジャーナルには本文を入れず、復旧blobの参照を記録する。

主なイベント：

```text
PLAN_PREPARED
RECOVERY_READY
REMOTE_OBJECTS_VERIFIED
REMOTE_COMMIT_IN_FLIGHT
REMOTE_COMMIT_CONFIRMED
LOCAL_APPLY_STARTED
LOCAL_APPLY_VERIFIED
CHECKPOINT_SAVED
RUN_COMPLETED
RUN_BLOCKED
RUN_INTERRUPTED
OUTCOME_UNKNOWN
```

`REMOTE_COMMIT_IN_FLIGHT`は通信を送る前に保存する。
`LOCAL_APPLY_STARTED`はLocalの変更前に保存する。
処理後のレシートがない場合は未実施と決めつけず、Remote/Localを再読込して実際の結果を確認する。

sequenceは当該端末・Vault内の全runで通算する単調増加整数とし、runごとに0へ戻さない。`lastAppliedJournalSequence`もこの通算番号を指す。新しいrunの最初のイベントも直前の有効イベントのハッシュを参照する。

イベントの破損・連番欠落がある場合、該当実行を`NEEDS_REVIEW`とする。
通常の診断ログをOFFにしても、安全ジャーナルは無効にしない。

## 7.9 復旧レシート

```typescript
interface RecoveryReceipt {
  format: "svsync-recovery";
  schemaVersion: 1;
  operationId: UUID;
  runId: UUID;
  originalPath: CanonicalPath;
  reason: "overwrite" | "conflict" | "delete" | "interrupted";
  beforeSha256: Sha256;
  beforeSize: number;
  plannedAfterSha256: Sha256 | null;
  baseRemoteCommitId: UUID;
  createdAtUtc: string;
  verified: boolean;
}
```

`verified=true`は実際に復旧本文を読み戻してハッシュ検証した後だけ設定する。
記録だけあって本文がない場合は復旧可能と表示しない。

## 7.10 形式更新・互換性

- 自動で古いRemoteを新形式に書き換えない。
- 形式更新前にRemoteの読み取り専用エクスポートとLocalのバックアップを確認する。
- 変更理由、新たに必要なクライアント機能、旧版へ戻れない可能性を表示する。
- 旧クライアントの動作は「未知の必須機能を見たら停止」で統一する。
- `attachments-v1`、`conflict-copy-v1`、`tombstones-v1`を初めて必要とする公開更新は、通常同期とは別の承認を必要とする。
- アプリのバージョン番号だけで読み書きの互換性を推測しない。

## 7.11 ログ共有とプライバシー

初期MVPのテレメトリーは実装しない。クラッシュの自動送信も実装しない。

共有用の診断出力では、ファイル名・パス・バケット名・アカウントIDを初期値で伏せる。
本文のハッシュも情報の照合に使われ得るため、初期値では伏せる。
ユーザーが内容を確認してから手動で出力する。

元の生ログをそのままGitHub Issueへ自動投稿する機能を作らない。

# 8. エラー・再試行

## 8.1 エラーの基本方針

エラーを`[]`、空文字、null、ファイル不在へ変換して正常扱いしない。
利用者向けの説明と、機械判定用のエラーコードを分離する。

**ERR-001** 一時的な障害は有限回の再試行を行う。
**ERR-002** 設定・権限・形式・整合性の問題は、同じ条件で自動再試行し続けない。
**ERR-003** 副作用のある通信が結果不明になった場合、再送より先に実際のRemote状態を確認する。
**ERR-004** エラーのために安全チェックを外す、強制上書きする、baselineを捨てる、といった自動修復はしない。

## 8.2 エラー一覧

| コード | 原因・検出条件 | 自動対応 | 利用者向けの案内 |
|---|---|---|---|
| `E_OFFLINE` | 通信できない | 読み取りは有限再試行 | 接続後に再実行。ノートは削除しない |
| `E_TIMEOUT` | 要求が期限内に完了しない | GETは再試行、PUTは結果確認 | 処理の結果を確認中/要確認と表示 |
| `E_RATE_LIMIT` | HTTP 429等 | Retry-Afterを尊重 | 利用制限により停止・延期 |
| `E_REMOTE_TRANSIENT` | HTTP 408、500、502、503、504 | 有限再試行 | 一時的な接続先障害 |
| `E_AUTH` | 401、無効/失効した資格情報 | 再試行停止 | 認証情報を確認 |
| `E_PERMISSION` | 403、AccessDenied | 再試行停止 | バケットと権限を確認 |
| `E_SIGNATURE` | SignatureDoesNotMatch等 | 再試行停止 | 接続先・資格情報・端末時計を確認 |
| `E_CONFIG` | endpoint・bucket等が不正 | 送信前に停止 | 設定項目を示す |
| `E_CAPABILITY` | 条件付きPUT等の必須能力が使えない | 書き込み禁止 | 対応検証が必要 |
| `E_REMOTE_HEAD_MISSING` | 既存Remoteのheadが404 | 新規作成しない | 復旧・接続先の確認 |
| `E_REMOTE_ENTRY_LOST` | baselineのパスが削除記録なしに消えた | 停止 | Remote一覧に不整合がある |
| `E_REMOTE_BLOB_MISSING` | manifest参照先の本文が404 | 停止 | Remote本文の欠損。削除ではない |
| `E_REMOTE_BUSY` | CASの再計画上限に達した | 停止 | 他端末の同期完了後に再実行 |
| `E_REMOTE_HISTORY_CHANGED` | 世代巻戻り・不正な分岐等 | 停止 | 履歴の確認が必要 |
| `E_COMMIT_UNKNOWN` | 公開処理が成功したか不明 | 照合のみ | 確認できるまでLocalを変えない |
| `E_CHECKSUM` | 本文・JSONのハッシュ不一致 | 自動採用しない | 内容の整合性検査に失敗 |
| `E_METADATA_INVALID` | JSON形式・識別子・重複等が不正 | 停止 | メタデータ復旧が必要 |
| `E_FORMAT_UNSUPPORTED` | 未対応protocol/capability | 読み取り診断のみ | 全端末の版を確認 |
| `E_LOCAL_IO` | ローカルI/O・権限エラー | 変更停止 | 保存場所を確認 |
| `E_LOCAL_NO_SPACE` | 容量不足が検出された | 変更停止 | 空き容量・復旧領域を確認 |
| `E_RECOVERY_WRITE` | 復旧保存または検証失敗 | 上書き・退避禁止 | 復旧用コピーを作れない |
| `E_LOCAL_CHANGED` | 計画後にLocal内容が変化 | 計画無効化 | 編集内容を保持して再比較 |
| `E_LOCAL_PATH_OCCUPIED` | 新規作成先が既に存在 | 上書きしない | 同名ファイルを確認 |
| `E_PATH_UNSAFE` | 相対パス逸脱・内部領域等 | 書き込み禁止 | 無効なパスを表示 |
| `E_PATH_COLLISION` | ケース・Unicode・型の衝突 | 停止 | 自動改名せず整理を案内 |
| `E_UNSUPPORTED_ENCODING` | UTF-8を同じバイト列で扱えない | 同期保留 | 元ファイルの文字コードを確認 |
| `E_LIMIT` | 件数・サイズ・API数等の上限 | 新規操作停止 | 超過した設計上限を表示 |
| `E_CONFLICT` | 双方変更、削除対編集等 | 初期版は停止 | 両方を保持して解消を案内 |
| `E_JOURNAL_INVALID` | 未完了記録の破損・欠落 | 停止 | 自動再開せず診断へ |
| `E_CANCELLED` | ユーザーの中止・実行世代変更 | 新規操作を止める | 確定済み部分を表示 |
| `E_INTERRUPTED` | アプリ終了・モバイル停止 | 次回に状態照合 | 前回処理を確認して再開 |

エラーコードはHTTPの番号だけで決めず、S3のエラー名と操作の文脈を併用する。
通信ライブラリ固有のエラーオブジェクトをそのままUIや共有ログへ出さない。

## 8.3 404・412の文脈別処理

| 応答 | 対象 | 解釈 |
|---|---|---|
| 404 | 明示した新規初期化のhead | 新規候補。ただしprefix検査・CASが必要 |
| 404 | 一度接続済みのhead | 異常。空Remoteへリセットしない |
| 404 | manifest/commit/参照済みblob | 欠損。ノート削除の指示ではない |
| 404 | 未保存の新しいblob候補への存在確認 | 作成候補。後続は条件付きPUT |
| 412 | 不変blob/manifest/commit作成 | 既存内容をGETして照合 |
| 412 | head更新 | 別更新または前回再試行の成功を確認 |

すべての404を「ファイルなし」、すべての412を「通信障害」とする共通処理は禁止する。

## 8.4 再試行の初期値

以下はアプリケーション側の設計値であり、応答時間の保証ではない。

| 設定 | 初期値 |
|---|---:|
| 同一の通常要求の最大試行回数 | 初回を含め4回 |
| バックオフ基準 | 1秒 |
| バックオフ上限 | 30秒 |
| ジッター | 0〜上限の乱数 |
| メタデータ要求の論理タイムアウト | 30秒 |
| 本文要求の論理タイムアウト | 60秒 |
| 1回の同期の実行予算 | 10分 |
| headの競合による再計画 | 連続3回まで |

再試行番号`k=0,1,2`に対し、通常の待機を次で求める。

```text
delay = uniform(0, min(30秒, 1秒 × 2^k))
```

`Retry-After`が有効なら、それより短い時間で再試行しない。
HTTP日付の場合は可能な範囲でレスポンスのDateとの関係を使い、端末時計だけを信用しない。
待機時間が残りの実行予算を超える場合は、待機を勝手に短縮せず、その同期を延期状態で終了する。

手動で再実行された場合も、未解決の結果不明PUTがあれば先に照合する。

## 8.5 操作別の再試行規則

| 操作 | 再試行の条件 |
|---|---|
| GET/HEAD | 同じ対象への有限再試行。最終失敗は欠損扱いしない |
| LIST | 失敗した完全一覧を捨て、用途に応じて最初から再検査 |
| 不変オブジェクトPUT | 同じキー・同じ本文・If-None-Matchを維持。412は内容確認 |
| head PUT | 第6.10節で結果照合した後のみ。無条件再PUTは禁止 |
| Localの新規作成 | 保存先を読み直して期待ハッシュと一致すれば完了扱い。一致しなければ上書きしない |
| Localの更新 | 旧内容・新内容・現在内容を再比較。前回処理を盲目的に繰り返さない |
| Localの退避 | 元パスと退避先を両方確認し、移動済みか・新規編集かを判定 |

同じ操作のoperationIdは保持する。単純な再試行のたびに新しい復旧レシートや競合ファイルを無制限に作らない。
再計画で内容そのものが変わった場合は、新しいplanIdと必要な新操作を生成する。

## 8.6 中止とiPhoneの中断

「中止」は、今後の新しい操作を止めることを意味する。すでに完了したRemote/Localの変更をすべて元に戻す機能ではない。

- 要求を本当に中断できる場合は中断する。
- 中断できないPUTは`OUTCOME_UNKNOWN`として残す。
- 実行ごとにrunIdと実行世代を持ち、古い非同期コールバックからLocalやbaselineを変更させない。
- アプリが前面でない、または実行継続を確認できない場合、新しい書き込みを始めない。
- アプリが強制終了した場合、終了通知が来ることを前提としない。
- 次回起動は`RECOVER_PENDING`を通常同期より先に実行する。

MVP 0.1は手動同期であり、iPhoneのアプリを閉じた後まで同期が続くとは説明しない。

## 8.7 再起動時の復旧手順

1. ローカルidentityとチェックポイントを検証する。
2. 未完了runとpending planを列挙する。
3. Remoteに結果不明の公開処理があれば、最初にcommitの採用状況を確認する。
4. Local変更の記録があれば、現在本文と期待する旧/新本文を比較する。
5. 完了が証明できる操作だけを確定する。
6. 現在の内容が旧/新のどちらでもない場合、第三の版として保全し、上書きしない。
7. 各操作を確定・保留した後に新しい通常同期計画を生成する。

### 中断位置別の期待動作

| 中断位置 | 次回の動作 |
|---|---|
| blobだけ保存済み、head未更新 | 未公開物として扱う。ノート一覧へ勝手に追加しない |
| head更新の応答待ち | Remote状態を確認し、成功/未採用/不明に分類 |
| head公開済み、Local未反映 | 現在LocalとRemoteを再比較して不足分を反映 |
| Local書き込み済み、完了レシートなし | 実本文のハッシュで判定し、重複操作を避ける |
| Localがその後さらに編集済み | その内容を保持し、競合/再計画へ |
| baseline保存途中 | 正常なチェックポイントとジャーナルで再照合 |
| 復旧ファイルの保存途中 | 未検証として採用しない。元のノートを変更しない |

## 8.8 結果表示

| 表示状態 | 意味 |
|---|---|
| `COMPLETED` | 当該計画の対象をすべて確認できた |
| `NO_CHANGES` | 対象内容に変更なし |
| `COMPLETED_WITH_EXCLUSIONS` | 正常に完了したが、添付等の対象外がある |
| `BLOCKED` | 実行前の安全検査で止めた |
| `PARTIAL` | 一部の公開/反映は完了、残りは未完了 |
| `NEEDS_REVIEW` | 競合または結果不明のため確認が必要 |
| `CANCELLED` | 新規操作を中止。確定済み変更は残る場合がある |

「全端末が最新」「すべて安全に保管済み」といった、当該端末から確認できない状態を表示しない。

UIには対象件数、公開済み件数、この端末への反映済み件数、保留、対象外、最初の原因エラーを表示する。
同じエラーを大量のポップアップにせず、一つの状態画面に集約する。

# 付録C. iCloud要件との接点

構想で合意したとおり、iCloudの要件仕様は現在の設計段階で別文書として整理し、技術方式の確定と実装・試験は後段へ回す。

この8項目で共用を想定する部品は、パス検査、内容ハッシュ、復旧レシート、ジャーナル、診断表示である。
R2のCASやmanifest公開処理を、iCloud Driveへそのまま当てはめる設計にはしない。

iCloud安全モードが将来実装されても、Apple側の同期処理を本プラグインが確実に停止できるとは前提にしない。
「iCloudによる大量削除そのものを事前に防止する」とは未検証の段階で仕様・宣伝に記載しない。
本プラグイン自身の書き込み停止と、外部同期の停止を明確に区別する。

現在使用中のiCloud Vaultは、R2版の開発を理由に移動する必要はない。初期開発は別のテストVaultと別のRemote領域で行う。

# 付録D. 採用案と代替案の記録

| 論点 | 本書の採用案 | 今は採用しない案・理由 |
|---|---|---|
| 差分判定 | L/R/Bの内容比較 | mtimeだけ：時計ずれ・同時変更を扱えない |
| Remoteの公開 | 不変本文+不変一覧+head CAS | 複数ファイルの無条件PUT：途中状態・更新消失の管理が難しい |
| 同時更新 | 楽観的なCASと再計画 | 単純ロックファイル：作成競合・期限切れ・中断時の設計が増える |
| 復旧 | 世代本文とジャーナル、別名復元 | 全端末ワンクリックRollback：対象範囲と整合性が未確立 |
| 削除 | tombstoneとローカル退避 | 不在なら削除：読込失敗や空端末を誤解釈する |
| 初回同期 | 追加・比較・競合停止 | 全体の一方優先：既存データを無断上書きしやすい |
| 費用 | 小さい上限・手動同期・利用量表示 | 無料保証：アカウント全体の課金を制御できない |
| 旧版互換 | 新prefixへ確認済みコピーから移行 | Remote形式の無検証の置換：データ/ライセンス/暗号化のリスク |

manifest全体を毎回保存する方式は、小規模・手動中心の初期検証で安全性を説明しやすい一方、規模が増えると容量・更新競合・読み込み負荷が増える。
将来、ファイル別manifestや増分ログに変える場合は、公開原子性、削除、初回参加、結果不明PUTの受入試験を維持したうえで新しいプロトコルとして審査する。

# 付録E. 用語集

| 用語 | 説明 |
|---|---|
| baseline | その端末とクラウドで、最後に共通だと確認できたファイルの版 |
| hash / SHA-256 | 本文の違いを判定するための内容由来の識別値 |
| ETag | R2から返る、そのオブジェクトへの条件付き操作に使う値 |
| CAS | 読んだ状態から変わっていない場合だけ更新する方法 |
| blob | ノート本文などのバイト列を保管するオブジェクト |
| manifest | ファイルパスと本文の版の対応一覧 |
| head | 現在採用しているcommitとmanifestを指す記録 |
| commit | 一回のRemote状態の公開候補・履歴を表す記録 |
| tombstone | 単なる不在とは違う、明示的な削除の記録 |
| journal | 何を実行しようとし、どこまで確認できたかの記録 |
| 冪等性 | 同じ操作を確認・再試行しても、不要な重複や別結果を生まない性質 |
| capability | そのRemoteを安全に扱うためにクライアントが理解すべき機能 |
| Fail-safe | 判断できないときは、推測して変更するより停止する方針 |
| Recovery Assistance | 過去の本文や記録を用いた復旧支援。全端末自動巻戻しではない |
