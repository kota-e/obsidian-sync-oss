# Obsidian同期OSSプロジェクト 現状整理

## 1. このドキュメントの目的

この文書は、Remotely Saveを起点として新しいObsidian同期OSSを検討している現時点の状況、判断、合意事項、制約、今後の進め方を整理したものです。

今後は、この文書を土台として以下の順番でドキュメントを作成します。

1. 現状整理ドキュメント（本書）
2. 構想仕様書
3. 詳細仕様書
4. テスト仕様書
5. Codex実装ガイド

7. OSS公開・ローンチ

最終的には、Codexへ詳細仕様書一式を渡すことで、実装方針を正確に理解し、開発を進められる状態を目指します。

---

# 2. プロジェクトの発端

ObsidianのVaultをWindows PCとiPhoneで安全に同期・保管する方法を検討してきました。

これまで候補として、主に以下を検討しました。

- iCloud Drive
- OneDrive
- Google Drive
- Cloudflare R2
- Obsidian Sync
- Remotely Save
- Self-hosted LiveSync
- Syncthing
- Git系同期
- ローカルVault＋クラウドバックアップ

しかし、Windows＋iPhone＋低コスト＋高信頼性という条件を同時に満たす方法には、それぞれ課題がありました。

特に、現在利用しているiCloud Drive上のVaultについては、Windowsとの組み合わせで競合・重複・破損リスクが懸念されています。

その過程で、Remotely Saveが以下の点で非常に魅力的であることを再確認しました。

- WindowsとiPhoneの両方に対応
- 各端末にローカルVaultを持てる
- クラウドを中継地点として利用できる
- Cloudflare R2などのS3互換ストレージに対応
- OneDrive、WebDAV等にも対応
- 自動同期
- 手動同期
- 暗号化
- 基本的な競合検知

一方で、Remotely Saveの保守状況には大きな懸念があります。

# 3. Remotely Saveの現状認識

## 3.1 開発・保守状況

確認した範囲では、Remotely Saveの正式リリースと本体コード更新は2024年を最後に大きく停滞しています。

ただし、元開発者はプロジェクトを完全に放棄したとは明言しておらず、継続意思を示した発言も確認されています。

したがって、現時点の評価は次の通りです。

- 「完全に終了したプロジェクト」とは断定しない
- 一方で、長期間の継続的な保守が行われている状態でもない
- 2026年にも外部開発者から修正PRが提出されている
- 重要な安全性修正を含むPRが未マージのまま残っている
- 「今動くこと」と「今後も安心して保守されること」は分けて考える

## 3.2 既存PRについて

既存の未マージPRには、以下のような重要な修正提案が含まれています。

- 通信エラー時の誤判定によるデータ消失リスク
- 削除失敗後にファイルが復活する問題
- 競合処理時の上書きリスク
- 同期を停止させるクラッシュ
- S3での更新日時処理に関する問題
- メタデータ保存ミス
- 特殊フォルダ除外処理の不具合

今後のFork版では、これらをそのまま無条件で取り込むのではなく、

1. 不具合の再現
2. 修正内容の精査
3. ライセンス確認
4. 自動テスト
5. 実機テスト
6. 採用判断

という流れで取り込む方針です。

# 4. プロジェクトの基本方針

本プロジェクトは、単なる「Remotely Saveの修正版」ではなく、

> Obsidianのノートを、複数端末・複数ストレージ間で安全に同期し、データ消失を最優先で防ぐOSS

として育てる方針です。

特に、安全性を最優先します。

## 4.1 最優先する価値

1. データを消さない
2. 競合時に勝手に片方を捨てない
3. 通信障害を「削除」と誤認しない
4. 大量削除などの異常を検知して停止できる
5. 何が同期されたか追跡できる
6. 問題発生時に戻せる
7. ユーザーが同期前に結果を確認できる
8. 特定クラウドへのロックインを避ける

---

# 5. 元Remotely Save作者への敬意と権利方針

このプロジェクトでは、元Remotely Save作者およびコントリビューターの成果を尊重します。

目的は、元作者の成果・売上・権利を奪うことではありません。

## 5.1 基本原則

### 原則1：出自を隠さない

README等に、Remotely Saveを起点とした派生プロジェクトであることを明記します。

例：

> Originally based on Remotely Save by fyears and its contributors.

元プロジェクトへのリンク、著作権表示、ライセンス表示を維持します。

### 原則2：「公式後継」を名乗らない

元作者の許諾なく、以下のような表現は使用しません。

- Official successor
- Remotely Save 2
- 公式後継版

独自のプロジェクト名を付けます。

### 原則3：Proコードを不正利用しない

Remotely Saveは現在、コード領域によってライセンスが異なります。

- `src`
- `tests`
- `docs`
- `assets`

などはApache License 2.0。

一方、

- `pro`

配下はPolyForm Strict License 1.0.0です。

そのため、Pro部分を自由にFork・改変・再配布できるものとして扱いません。

### 原則4：有料機能の無料化を目的にしない

このプロジェクトの目的を、

> Remotely Saveの有料機能を無料で配る

とはしません。

目的は、

> OSSとして利用可能な部分を、安全性重視で維持・発展させる

ことです。

### 原則5：可能な場合は元プロジェクトにも還元する

元Remotely Saveにも有用な修正がある場合は、可能なら元リポジトリへのPRも検討します。

元作者が開発に復帰した場合にも、敵対的なプロジェクト運営は行いません。

# 6. ライセンス上の重要事項

現在のRemotely Save最新版を、そのまま全体Forkして好きに変更する方針は採用しません。

理由は、同期中核の一部が制限付きライセンス領域に存在するためです。

現時点では、以下を土台候補とします。

## 候補A：ライセンス変更前のApache版Remotely Save

メリット：

- 元Remotely Saveとの構造的な連続性が高い
- Remotely Saveの設計思想を引き継ぎやすい
- OSSとして改変可能な範囲が明確

デメリット：

- 古い
- 現在のObsidianとの互換性確認が必要
- 新しい修正を手作業で取り込む必要がある

## 候補B：Apache 2.0の派生版

例としてRemotely Sync等。

メリット：

- Apache 2.0として公開されている派生版が存在する
- 既存の変更を参考にできる

デメリット：

- Remotely Saveとの互換性や設計差を確認する必要がある
- 安定性を独自に検証する必要がある

## 現時点の方針

構想仕様書を作成した後、

- ライセンス
- コード構造
- 変更量
- テスト可能性
- 現行Obsidianとの互換性

を比較し、ベースリポジトリを正式決定します。

# 7. 想定する技術構成

まずはCloudflare R2 / S3互換ストレージを中心に開発します。

初期イメージ：

```text
Windows Obsidian
      ↕
ローカルVault
      ↕
本プロジェクトの同期プラグイン
      ↕
Cloudflare R2 / S3
      ↕
本プロジェクトの同期プラグイン
      ↕
iPhoneローカルVault
      ↕
iPhone Obsidian
```

Cloudflare R2上のファイルを直接Vaultとして開く方式ではありません。

各端末にローカルVaultを持ち、R2は同期の中継地点として利用します。

# 9. 安全性機能の方向性

本プロジェクトの最大の差別化要素は、安全性です。

## 9.1 Dry Run

実際に変更する前に、

- アップロード
- ダウンロード
- 削除
- 名前変更
- 競合

の予定を確認できるようにします。

## 9.2 Mass Delete Guard

大量削除を検知した場合、自動的に同期を停止します。

例：

- 100件以上削除
- Vault全体の10%以上削除

など。

具体的なしきい値は詳細仕様書で決定します。

## 9.3 Network Failure Guard

通信障害、API障害、一覧取得失敗を、

> リモートからファイルが削除された

と誤認しない設計にします。

## 9.4 Conflict Preservation

同一ファイルが複数端末で編集されていた場合、片方を勝手に消さず、可能な限り双方を保存します。

## 9.5 Sync Journal

同期履歴を記録します。

記録候補：

- 時刻
- 端末
- ファイル
- 操作
- 結果
- エラー
- 同期元
- 同期先

## 9.6 Rollback / Recovery

同期事故から復旧しやすい設計を目指します。

実現方式は構想仕様書・詳細仕様書で検討します。

# 10. iCloudについて

iCloud対応は、実装を後回しにします。

ただし、仕様策定は後回しにしません。

つまり、

> 仕様書には最初からiCloud対応の構想と詳細設計を含める。
> 実装・テストだけを後のPhaseに回す。

という方針です。

## 10.1 iCloudが他のBackendと異なる点

Cloudflare R2 / S3 / OneDrive / WebDAVなどは、基本的にプログラムからAPI経由でアクセスするリモートストレージです。

iCloud Driveは同じ扱いができない可能性が高く、別の設計が必要です。

そのため、同じプロジェクト内でも以下のように分離する可能性があります。

### 通常同期モード

- Cloudflare R2
- S3
- OneDrive
- WebDAV
- その他API型ストレージ

### iCloud安全モード

- iCloud Vaultの監視
- 重複検出
- 競合検出
- 大量削除検出
- バックアップ
- 異常通知
- 復旧支援

将来的に、技術的に可能で安全な方法が確認できた場合は、iCloudを同期Backendとして扱う可能性も再検討します。

# 12. テスト方針

本番Vaultを最初から使用しません。

## 開発初期

専用のテストVaultを使用します。

## テスト例

### 正常系

- Windowsで新規作成 → iPhoneへ同期
- iPhoneで新規作成 → Windowsへ同期
- 編集
- 名前変更
- フォルダ移動
- 添付ファイル追加
- 削除

### 異常系

- 同期中にネットワーク切断
- APIエラー
- R2障害
- 認証エラー
- ファイル一覧取得失敗
- 同一ファイルを両端末で編集
- 同一ファイルを片側で削除し、もう片側で編集
- 空の新端末を追加
- 大量ファイルを削除
- 同期途中でObsidian終了
- 同期途中でiPhoneアプリが停止

## 合格条件

「同期できた」だけでは合格としません。

最重要条件は、

> 異常時にもデータが意図せず失われないこと

です。

# 18. プロジェクトの成功条件

このプロジェクトは、単に「同期できた」ことで成功とはしません。

成功条件は以下です。

1. WindowsとiPhoneで安定して同期できる
2. Cloudflare R2を安全に利用できる
3. 通信障害でファイルを削除しない
4. 競合時にデータを失わない
5. 異常な大量削除を防止できる
6. 同期履歴を確認できる
7. バージョン更新後も自動テストで安全性を確認できる
8. 本人以外のObsidianユーザーも導入できる
9. 元Remotely Save作者・Contributorの権利を尊重できている
10. 継続的に保守できる構造になっている
